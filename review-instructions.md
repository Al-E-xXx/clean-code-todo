# Инструкция для AI-помощника: ревью решения по заданию «Clean Code»

Ты ревьюишь решение учебного задания «Clean Code» (TODO-приложение). Помощник **не редактирует
файлы**: он только анализирует и объясняет. Решение принимает человек.

## Контекст

Статическое приложение без фреймворков и сборки: `index.html`, `style.css`, `app.js`,
`remove.svg`, `eisenhower-matrix.jpg`. Приложение работает и должно продолжать работать: задачи
добавляются в список «Todo», редактируются, удаляются, чекбокс переносит задачу в «Completed»,
снятие чекбокса возвращает в «Todo», пустая задача не добавляется.

Работа велась в ветке `clean-code-todo` от `main`. В `main` лежит исходный (плохой) код, в ветке —
исходный код плюс последовательность правок. Настройки инструментов: `eslint.config.js`,
`.prettierrc`, `.prettierignore`, `.husky/pre-commit`, `package.json`, `.gitignore`. Проверка CI —
`.github/workflows/check.yml`.

Полезные команды (только чтение):

```
git log --oneline main..HEAD
git show <хеш>
git diff main..HEAD -- app.js index.html style.css
npm run lint
npx prettier --check .
```

## Цель

Найти в текущем решении замечания, которые относятся к категориям задания, и сформулировать их так,
чтобы человек мог решить: принимать или отклонять. Ожидаемый результат — отчёт в файле
`review-report.md`, а не исправленный код.

Две вещи проверяются независимо и обе нужны:

1. **Остались ли проблемы из категорий задания** в итоговом коде.
2. **Не сломано ли и не противоречит ли требованиям** то, что уже сделано (в том числе лишние
   изменения, которые меняют поведение или вид).

## Границы

Проверять:

- `app.js`, `index.html`, `style.css` — итоговое состояние;
- историю правок: `git log --oneline main..HEAD`, `git diff main..HEAD`; каждое смысловое изменение
  должно быть отдельным читаемым коммитом с сообщением по конвенции
  (`type: описание`, повелительное наклонение, описание отражает суть, а не «fix»/«update»);
- файлы настройки инструментов — на соответствие требованиям задания;
- риск изменения поведения: любое изменение, которое может поменять вид или работу приложения.

Категории, по которым группируются замечания:

1. мёртвый код (не вызывается, не читается, атрибут без использования);
2. дублирование обработчиков;
3. дублирование логики;
4. имена, которые не читаются без комментариев;
5. комментарии, которые пересказывают код;
6. функции, которые не читаются целиком;
7. прочее: несоответствие требованиям задания, сообщения коммитов, риск для поведения.

Не трогать и не предлагать:

- не менять `.github/workflows/check.yml` и ветку `main`;
- не переписывать приложение на фреймворк, не добавлять сборщик, TypeScript, модули, тесты,
  запросы на сервер — этого в задании нет;
- не предлагать правки, которые меняют поведение или внешний вид приложения;
- не предлагать разметку «для галочки» вне задания (`alt`, `lang`, `meta`, `DOCTYPE`,
  семантические теги), если её требует только общий вкус;
- не трогать форматирование: пробелы, переносы строк, кавычки, пустые строки — это зона Prettier,
  `npx prettier --check .` проходит;
- не дробить функции только потому, что они длинные, и не объединять код только потому, что он
  похож; объединение нужно обосновать общим смыслом, иначе это дублирование;
- не предлагать переименования, после которых код читается не лучше;
- не считать проблемой то, что уже исправлено: перед замечанием проверять по `main..HEAD`, нет ли
  такого коммита;
- не править файлы и не запускать команды с записью (`--fix`, `prettier --write`, `git commit`).

Не придумывай замечания, чтобы заполнить категории. Если категории чистые — так и напиши.

## Критерий готовности

Ревью закончено, если выполнены все пункты:

- по каждой из семи категорий есть вывод: замечания или «замечаний нет» с указанием, где именно
  смотрели (одна-две строки);
- каждое замечание содержит все четыре части (см. «Формат вывода») и конкретное место: файл, имя
  функции или селектор/тег, номер строки, короткую цитату кода (до 3 строк);
- каждое замечание проверяемо: по нему можно сказать, обнаружено оно или нет, глядя в код;
- в отчёте нет дублей (одно и то же в разных категориях) и нет замечаний про уже исправленное;
- ни одно замечание не требует менять поведение, вид приложения или файлы вне границ;
- замечания отсортированы по влиянию на читаемость и безопасность правок, самых важных не больше
  десяти; всё остальное — в раздел «мелочи» одной строкой каждое;
- отчёт записан в `review-report.md`, объём отчёта позволяет прочитать его за один подход.

## Формат вывода

Один файл в корне проекта — `review-report.md`, на русском. Не менять никакие другие файлы.

```markdown
# Ревью решения: clean-code-todo

## Итог

таблица: категория → сколько замечаний, одна строка пояснения

## Замечания

### Категория: <название из списка выше>

#### <номер>. <короткий заголовок>

- **Место:** `app.js`, функция `...`, строка `...`
- **Проблема:** что именно тяжело читать или чем это опасно
- **Условие, при котором проявляется:** при каком изменении или сценарии проблема вылезает наружу
- **Как проверить исправление:** что увидеть в коде и как убедиться, что поведение не изменилось

## Мелочи

одна строка на замечание

## Вопросы к человеку

что нельзя понять из кода и что нужно решить автору
```

Не пиши готовый код замены. Допустимо указать направление: что убрать, что объединить, какое имя
стало бы понятнее — и как проверить, что поведение осталось прежним.
